## Методологія
Тестовано на рівні API (curl) з реальним supplier_admin-юзером: провайдер-токеном створено новий
supplier-tenant (`POST /api/provider/tenants`, business_type=supplier) + user з роллю supplier_admin
і відомим паролем (креденшели seed-постачальників alpha/beta@supplier.local — з попередніх QA-сесій,
пароль невідомий, тому створено свіжого юзера). Тестові tenant/user/supplier/items видалено після
прогону (DELETE напряму в БД).

Не покрито: PUT/update існуючого **legacy** товару (одного з `alpha@supplier.local`, category=null з
TASK-275) через сам cabinet — немає credentials для seed-юзера alpha, а адмінський
`MarketplaceAdminController` не має PUT для items (лише POST create + DELETE) — це pre-existing
обмеження, поза скоупом TASK-293..297. Backward-compat для read підтверджено (item рендериться коректно
без category/attributes), backward-compat для write підтверджено на новоствореному без-категорійному товарі
(сценарій 4 у своєму тесті).
