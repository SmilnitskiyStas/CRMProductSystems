# Повний аналіз конкурентної сторінки «Аналіз аудиторії»

## 1. Призначення документа

Це аналіз четвертої з чотирьох сторінок конкурентного аналітичного сервісу Uployal — `Аналіз аудиторії`.

Сторінку досліджено у живому embed-інтерфейсі. Додатково використані локальні контрольні стани цієї самої сторінки для перевірки ненульового сегмента.

Перевірено:

- початковий стан;
- введення списку ID;
- завантаження CSV/TXT/TSV;
- автоматичне визначення колонки ID;
- дедуплікацію;
- поведінку неправильних і невідомих ID;
- вибір післякампанійного періоду;
- автоматичну побудову рівного періоду `до`;
- верхні KPI;
- вкладку `Огляд`;
- вкладку `Активність R/F/M`;
- вкладку `Міграція сегментів`;
- графік щоденного обороту;
- статуси сегмента;
- автоматичні рекомендації;
- таблицю споживачів;
- сортування і ліміт Top-200;
- RFM-діаграми та матрицю переходів;
- позитивний, негативний і нульовий результат;
- відмінність між чернеткою списку та вже проаналізованою аудиторією;
- методологічні обмеження before/after аналізу;
- вимоги до власної реалізації.

У документ не перенесені індивідуальні ID споживачів, імена, телефони або сесійний токен.

## 2. Роль сторінки у продукті

Сторінка оцінює поведінку наперед визначеної аудиторії після маркетингової кампанії.

Користувач повинен мати список ID людей, на яких була запущена кампанія. Система не формує аудиторію сама — це робить попередня сторінка `Підготовка аудиторії` або зовнішня CRM/CDP.

Сторінка відповідає на запитання:

- скільки грошей принесла вибрана аудиторія після кампанії;
- як змінився оборот проти такого самого періоду до кампанії;
- скільки неактивних клієнтів повернулося;
- скільки активних клієнтів зберегло активність;
- скільки активних клієнтів перестало купувати;
- як змінились чеки, оборот, середній чек і давність;
- як люди мігрували між RFM-сегментами;
- які наступні маркетингові дії пропонує система.

Фактично це інструмент **before/after аналізу завантаженого сегмента**.

## 3. Загальний сценарій роботи

1. Користувач вставляє ID або завантажує файл.
2. Сторінка розпізнає та дедуплікує ID.
3. Користувач обирає період `після` кампанії.
4. Система автоматично будує безпосередньо попередній період такої самої тривалості.
5. Користувач натискає `Аналізувати сегмент`.
6. Система зберігає застосовану версію аудиторії.
7. Рахуються KPI до та після.
8. Клієнти розподіляються за поведінковими статусами.
9. Для кожного ID визначається RFM-сегмент до та після.
10. Виводяться три вкладки звіту та рекомендації.

## 4. Початковий стан

До завантаження аудиторії показуються:

- перемикач `Список ID / Файл`;
- період `після` кампанії;
- автоматично розрахований період `до`;
- блок `Завантаження сегменту`;
- неактивна кнопка `Аналізувати сегмент`;
- порожня область з підказкою.

Підказка:

`Завантажте сегмент і натисніть «Аналізувати сегмент», щоб побачити ефект кампанії`.

Кнопка аналізу стає активною, щойно parser знайшов хоча б один цифровий ID.

## 5. Спосіб 1: «Список ID»

### 5.1. Поле введення

Використовується багаторядкове поле.

Підказка дозволяє:

- один ID у рядку;
- кілька ID через кому.

Демонстраційний формат:

```text
1024
2048
4096
```

### 5.2. Дедуплікація

Сторінка показує:

`Розпізнано N унікальних ID`.

Повторення однакового текстового ID видаляються.

Наприклад, комбінація трьох різних значень і одного дубліката дає три унікальні ID.

### 5.3. Реальний алгоритм розбору

Під час тесту parser виявився значно ширшим за опис у підказці.

Він розділяє значення не тільки за комами й новими рядками, але фактично витягує **кожну послідовність цифр** із тексту.

Підтверджена поведінка:

- `1;2` розпізнається як два ID;
- цифри всередині слова також стають ID;
- десяткове значення розбивається на дві цифрові частини;
- знак мінус відкидається;
- UUID із дефісами перетворюється на кілька окремих числових ID;
- значення з провідними нулями може залишитися окремим від значення без нулів.

Це небезпечна поведінка. Вона створює валідний на вигляд список із фактично пошкоджених ідентифікаторів.

### 5.4. Рекомендована поведінка нашої програми

Потрібна строга схема ID:

- тип ID визначається конфігурацією tenant-а;
- numeric ID приймає лише повністю цифровий token;
- UUID приймає повний UUID;
- значення не витягуються з довільного тексту;
- неправильні рядки показуються окремо;
- користувач бачить перші 20 помилок;
- перед аналізом показується кількість валідних, дубльованих і відхилених значень.

## 6. Спосіб 2: «Файл»

### 6.1. Формати

Файлове поле має accept:

`.csv, .txt, .tsv`.

Excel напряму не підтримується. Інтерфейс радить спочатку використати `Зберегти як CSV`.

### 6.2. Обмеження

На екрані вказано:

`до 50 000 ID`.

### 6.3. Автоматичне визначення колонки

Сторінка обіцяє автоматично розпізнати колонку з ID.

У тестовому CSV з колонкою `customer_id`:

- колонка була знайдена;
- два різні ID та один дублікат дали два унікальні ID;
- ім'я файлу відобразилося у зоні завантаження.

Точний пріоритет заголовків конкурент не розкриває.

Для власної програми краще:

1. Автоматично запропонувати найімовірнішу колонку.
2. Показати preview перших рядків.
3. Дати користувачу підтвердити або змінити колонку.
4. Показати результат валідації до запуску запиту.

### 6.4. Перемикання способу введення

Перемикання `Список ID / Файл` не обов'язково очищає вже розпізнаний draft. В одному тесті після переходу до файлового режиму залишилася кількість ID, розібраних із попереднього тексту.

Вибір нового файлу замінює draft списком із файлу.

## 7. Чернетка та застосований сегмент

Сторінка має два різні стани аудиторії:

1. **Draft** — ID, які зараз розпізнані в textarea або файлі.
2. **Analyzed segment** — ID, за якими побудований поточний звіт.

Після аналізу біля перемикача з'являється badge:

`N ID в аналізі`.

Якщо після цього змінити textarea або вибрати інший файл:

- напис `Розпізнано N унікальних ID` змінюється;
- старий звіт залишається;
- badge `ID в аналізі` залишається старим;
- новий список не застосовується без повторного натискання `Аналізувати сегмент`.

Це правильне розділення стану, але слабко підсвічене в UI.

Для власної програми потрібне явне повідомлення:

`Є незастосовані зміни аудиторії`.

Також бажано:

- візуально затемнювати старий звіт;
- показувати hash або версію сегмента;
- не дозволяти користувачу помилково вважати старі KPI результатом нового файлу.

## 8. Невідомі та неіснуючі ID

Це один із найважливіших результатів дослідження.

Сторінка не перевіряє існування ID під час імпорту.

Тест із 1 000 довільними числовими ID показав:

- `Розпізнано 1 000 унікальних ID`;
- `1 000 ID в аналізі`;
- нуль покупців;
- нуль обороту;
- усі 1 000 потрапили до `Не повернулись`;
- у RFM-таблиці вони відображалися як `Втрачені → Втрачені`;
- Top-200 містив самі невідомі ID із нульовими метриками.

Отже, сторінка не відрізняє:

- реального клієнта без покупок;
- ID, якого взагалі немає в tenant-і;
- помилково розібраний фрагмент числа.

### 8.1. Вплив на показники

Невідомі ID:

- збільшують розмір сегмента;
- зменшують частку покупців після;
- зменшують реактивацію;
- збільшують `Не повернулись`;
- збільшують `Втрачені → Втрачені`;
- спотворюють рекомендації;
- можуть створити помилковий висновок про провал кампанії.

### 8.2. Необхідне покращення

Перед аналізом наша система повинна розділити:

```text
uploaded_ids
matched_customer_ids
unknown_ids
duplicate_ids
invalid_tokens
```

У знаменники аналітики за замовчуванням мають входити лише `matched_customer_ids`.

Невідомі ID потрібно показувати в окремому downloadable error report.

## 9. Очищення

Кнопка `Очистити`:

- видаляє draft;
- видаляє застосований сегмент;
- прибирає badge `ID в аналізі`;
- приховує весь звіт;
- знову блокує кнопку аналізу;
- зберігає вибраний період;
- зберігає активний спосіб введення.

## 10. Період «після» кампанії

Користувач задає лише after-вікно.

У початковому контрольному стані:

- після: 26.04.2026–25.05.2026;
- до: 27.03.2026–25.04.2026;
- обидва вікна — 30 календарних днів.

### 10.1. Формула попереднього вікна

Дати включні.

```text
window_days = DATEDIFF(day, after_start, after_end) + 1
before_end = after_start - 1 day
before_start = before_end - (window_days - 1) days
```

Для 7-денного тесту:

- після: 11.07–17.07;
- до: 04.07–10.07;
- однакові 7 днів.

### 10.2. Календар

Календар показує два місяці та дозволяє натиснути спочатку початкову, потім кінцеву дату.

Швидкі варіанти:

- `Останні 7 днів`;
- `Останні 14 днів`;
- `Останні 30 днів`;
- `Поточний місяць`;
- `Минулий місяць`.

### 10.3. Зміна дати після аналізу

Якщо сегмент уже проаналізований, зміна періоду автоматично перераховує звіт для **застосованого сегмента**.

Важливий нюанс: якщо draft ID уже змінений, але ще не застосований, нові дати все одно перерахують старий analyzed segment.

### 10.4. Кнопка «Оновити»

Кнопка з'являється тільки після побудови звіту. Вона повторно завантажує поточний analyzed segment для вибраних дат.

## 11. Верхні KPI

Над вкладками показуються чотири картки:

1. `Гроші після кампанії`.
2. `Реактивовані`.
3. `Утримані`.
4. `Відпали`.

### 11.1. Гроші після кампанії

Показує:

- оборот сегмента у періоді після;
- кількість унікальних покупців після;
- відсоткову зміну обороту проти періоду до.

Формули:

`money_after = SUM(receipt_amount in after window for segment)`.

`buyers_after = COUNT(DISTINCT customer_id with purchases after)`.

`money_delta_pct = (money_after / money_before - 1) * 100%`.

Відсоток на картці показується з одним десятковим знаком.

### 11.2. Реактивовані

Умова:

`purchases_before = 0 AND purchases_after > 0`.

Картка показує:

- кількість реактивованих;
- частку від усіх неактивних до кампанії.

`reactivation_rate = reactivated / inactive_before * 100%`.

Якщо неактивних до не було, текст змінюється на `усі були активні до`.

### 11.3. Утримані

Умова:

`purchases_before > 0 AND purchases_after > 0`.

Картка показує частку від усіх активних до:

`retention_rate = retained / active_before * 100%`.

### 11.4. Відпали

Умова:

`purchases_before > 0 AND purchases_after = 0`.

Картка показує кількість, але не показує відсоток churn окремо.

### 11.5. Не повернулись

Є четвертий поведінковий стан, який не має верхньої картки:

`purchases_before = 0 AND purchases_after = 0`.

Він показується тільки у donut `Статус сегмента`.

### 11.6. Повний поділ сегмента

```text
segment_size = reactivated + retained + dropped + not_returned
buyers_after = reactivated + retained
active_before = retained + dropped
inactive_before = reactivated + not_returned
```

Текст довідки говорить, що чотири верхні картки ділять сегмент за поведінкою, але це формально неточно: перша картка є грошовою метрикою, а стан `Не повернулись` не має картки.

## 12. Контрольний сегмент із 42 ID

У контрольному ненульовому стані сторінка показала:

| Показник | Значення |
|---|---:|
| Розмір сегмента | 42 |
| Покупців після | 40 |
| Гроші після | 236 227 ₴ |
| Зміна обороту | -15,2% |
| Реактивовані | 1 |
| Реактивація | 100% із 1 неактивного |
| Утримані | 39 |
| Утримання | 95% активних до |
| Відпали | 2 |
| Не повернулись | 0 |

Перевірки:

`1 + 39 + 2 + 0 = 42`.

`1 + 39 = 40 покупців після`.

`39 / (39 + 2) ≈ 95,1%`.

## 13. Змішаний контроль невідомих ID

До валідного сегмента з 15 ID було додано 10 довільних невідомих ID.

Результат:

| Статус | Кількість | Частка від 25 |
|---|---:|---:|
| Реактивовані | 0 | 0% |
| Утримані | 14 | 56,0% |
| Відпали | 1 | 4,0% |
| Не повернулись | 10 | 40,0% |

Оборот і покупці валідної частини не змінилися, але всі аудиторні відсотки погіршилися.

Цей тест прямо підтверджує необхідність existence validation.

## 14. Вкладка «Огляд»

Вкладка містить:

- пояснення верхніх KPI;
- графік `Динаміка обороту: до vs після`;
- donut `Статус сегмента`;
- блок `Рекомендації — наступні кроки`.

## 15. Графік щоденного обороту

Підпис:

`Щоденна виручка сегмента, вирівняна по днях вікна`.

Серії:

- суцільна бірюзова/залита — після;
- сіра пунктирна — до.

Обидва вікна вирівнюються за порядковим номером дня:

```text
after_day_1 vs before_day_1
after_day_2 vs before_day_2
...
```

Вісь X підписана календарними датами after-вікна.

Вісь Y автоматично масштабується у гривнях і використовує скорочення `k` для тисяч.

Сума щоденних значень after-серії має дорівнювати KPI `Гроші після кампанії`.

### 15.1. Методологічний ризик

Рівна кількість днів прибирає лише різницю тривалості.

Вона не усуває:

- сезонність;
- різні дні тижня при вікні не кратному семи;
- свята;
- загальні акції;
- зміну цін;
- доступність товарів;
- зовнішні комунікації;
- природний тренд сегмента.

## 16. Donut «Статус сегмента»

У центрі показується загальний розмір analyzed segment.

Легенда містить лише ненульові категорії:

- `Реактивовані`;
- `Утримані`;
- `Відпали`;
- `Не повернулись`.

Для кожної категорії показуються:

- кількість;
- частка від повного uploaded/analyzed сегмента з одним десятковим знаком.

У контрольному сегменті 42:

- реактивовані — 1, 2,4%;
- утримані — 39, 92,9%;
- відпали — 2, 4,8%.

У змішаному сегменті невідомі ID потрапили до `Не повернулись`, що ще раз підтверджує відсутність перевірки існування.

## 17. Автоматичні рекомендації

Рекомендації формуються за правилами й змінюються відповідно до KPI.

### 17.1. Внесок у виручку

При ненульовому обороті:

- показується сума after;
- вказується кількість покупців після;
- сума називається прямим внеском аудиторії.

### 17.2. Успішна реактивація

При високій частці повернення текст повідомляє, що реактивація спрацювала, і радить масштабувати сценарій на схожі сплячі сегменти.

У 7-денному тесті:

- неактивних до — 1;
- реактивовано — 1;
- rate — 100%.

### 17.3. Слабка реактивація

При низькому rate текст радить:

- інший канал;
- інший оффер;
- сильніший стимул.

У змішаному тесті 0 із 10 неактивних повернулися.

В іншому 7-денному стані 2 із 13 повернулися, але 15% все одно було класифіковано як слабку реактивацію.

Точний поріг між `спрацювала` і `слабка` не розкритий.

### 17.4. Піднялись по RFM

Якщо є підвищення:

- показується кількість;
- рекомендується наступний рівень програми лояльності;
- мета — закріпити нову поведінку.

### 17.5. Знизились по RFM

Якщо знижень більше, ніж підвищень:

- система називає сегмент таким, що радше згасає;
- радить переглянути оффер;
- радить переглянути таймінг комунікації.

### 17.6. Оборот зріс

При позитивному delta:

`Виручка «після» вища за «до» — кампанія підняла продажі сегмента`.

У двоелементному контрольному тесті:

- after turnover — 5 720 ₴;
- delta — +138,0%;
- рекомендація округлила значення до 138%.

### 17.7. Оборот впав

При негативному delta:

- вказується округлений відсоток падіння;
- система говорить, що результат кампанії не досягнуто;
- радить переглянути механіку.

У контрольному сегменті 42 падіння -15,2% у рекомендації відображалось як 15%.

### 17.8. Обережність із рекомендаціями

Текст рекомендацій використовує причинні формулювання:

- `кампанія підняла продажі`;
- `результат активації`;
- `реактивація спрацювала`.

Однак сторінка не має контрольної групи. Тому такі висновки не доведені статистично.

## 18. Вкладка «Активність R/F/M»

Вкладка пояснює:

- `Recency` — як давно купував;
- `Frequency` — скільки разів купував;
- `Monetary` — на яку суму;
- з трьох вимірів формується RFM-сегмент.

Показуються чотири агреговані картки:

1. `Чеки`.
2. `Оборот`.
3. `Середній чек`.
4. `Давність (дн)`.

Кожна картка містить after-значення та процентну зміну проти before.

## 19. Чеки

`Чеки` визначені як кількість покупок.

Формула:

`checks_period = COUNT(DISTINCT receipt_id for analyzed segment)`.

`checks_delta_pct = (checks_after / checks_before - 1) * 100%`.

У контрольному сегменті 42:

- після — 1 043 чеки;
- зміна — -6,3%.

У двоелементному 7-денному тесті:

- до — 9;
- після — 13;
- `13 / 9 - 1 = +44,4%`.

## 20. Оборот

`turnover_period = SUM(receipt_amount)`.

Картка дублює грошову величину з верхнього KPI для after-вікна.

У контрольному сегменті 42:

- 236 227 ₴;
- -15,2%.

У 7-денному тесті:

- до — 2 403 ₴;
- після — 5 720 ₴;
- +138,0%.

## 21. Середній чек

Довідка прямо визначає:

`average_check = turnover / checks`.

У контрольному сегменті 42:

- після — 226 ₴;
- зміна — -9,5%.

У 7-денному тесті:

- після — 440 ₴;
- зміна — +64,8%.

Контроль:

`5 720 / 13 = 440 ₴`.

Ця картка використовує арифметичний середній чек, а не медіанний типовий чек зі сторінки `Цінові сегменти покупців`.

## 22. Давність

Визначення інтерфейсу:

`середня кількість днів від останньої покупки`.

Тут менше — краще.

Тому:

- негативний delta;
- стрілка вниз;
- зелений колір

трактуються позитивно.

У контрольному сегменті 42:

- після — 3 дні;
- зміна — -22,4%.

У 7-денному тесті:

- до — 2;
- після — 2;
- зміна — 0,0%.

### 22.1. Неясність формули

Інтерфейс не пояснює:

- від якої дати рахується recency;
- чи включаються клієнти без покупки у вікні;
- чи береться остання покупка за всю історію;
- чи нульові/невідомі ID виключаються із середнього.

У власній системі бажана формула:

`recency_at_period_end = period_end - last_purchase_date_on_or_before_period_end`.

Потрібно також показувати знаменник і правило для клієнтів без історії.

## 23. Таблиця «Споживачі сегмента»

Підпис:

`Топ-200 за оборотом «після» · сортуйте за колонками`.

### 23.1. Колонки

| Колонка | Значення |
|---|---|
| ID | ідентифікатор споживача |
| Чеки до | кількість чеків у before-вікні |
| Чеки після | кількість чеків у after-вікні |
| Оборот до | сума до |
| Оборот після | сума після |
| Сегмент до → після | RFM-клас в обох вікнах |

### 23.2. Сортування

ID не сортується.

Сортуються:

- чеки до;
- чеки після;
- оборот до;
- оборот після;
- перехід сегмента.

Інтерфейс не показує активний індикатор для початкового Top-200, хоча рядки фактично йдуть за after turnover.

### 23.3. Обмеження Top-200

Таблиця не має пагінації або експорту.

Для сегмента понад 200 ID показується лише 200 рядків.

Це означає:

- неможливо переглянути всіх відпалих із низьким after turnover;
- нульові рядки потраплять лише якщо активних менше 200 або при сортуванні;
- звіт не придатний як повний операційний список без іншого експорту.

У власному продукті потрібні:

- серверна пагінація;
- фільтр за переходом;
- пошук ID;
- повний контрольований експорт;
- явне повідомлення `показано 200 із N`.

### 23.4. Відсутність PII

На цій сторінці таблиця показує ID, але не показує ім'я або телефон.

Це кращий privacy-підхід, ніж на попередніх сторінках, але ID усе одно є персональним ідентифікатором.

## 24. RFM-сегменти

Сторінка використовує шість упорядкованих рівнів:

1. `Чемпіони`;
2. `Лояльні`;
3. `Перспективні`;
4. `Потребують уваги`;
5. `Сплять`;
6. `Втрачені`.

Порядок визначає, що вважається підвищенням або зниженням.

Клієнт без покупок у before-вікні в контрольному тесті отримав `Втрачені` до, а після покупки перейшов до `Чемпіони`.

Точні R/F/M-пороги на цій сторінці не пояснюються. Власна реалізація повинна використовувати той самий централізований RFM engine і ту саму версію правил, що й основний RFM-звіт.

## 25. Вкладка «Міграція сегментів»

Вкладка складається з:

- трьох KPI руху;
- donut сегментів до;
- donut сегментів після;
- матриці переходів.

### 25.1. KPI руху

Показуються:

- `Піднялись`;
- `Без змін`;
- `Знизились`.

Відсотки рахуються від повного analyzed segment і округлюються до цілого.

У контрольному сегменті 42:

- піднялись — 3, 7%;
- без змін — 35, 83%;
- знизились — 4, 10%.

Перевірка:

`3 + 35 + 4 = 42`.

### 25.2. Визначення руху

```text
rank_after < rank_before -> піднявся
rank_after = rank_before -> без змін
rank_after > rank_before -> знизився
```

У цьому записі менший rank означає кращий RFM-рівень.

## 26. Donut «Сегменти ДО» і «Сегменти ПІСЛЯ»

Це два snapshots того самого набору ID.

Вони показують чистий склад, але не показують індивідуальні переходи.

Наприклад, збільшення кількості чемпіонів на 4 не означає чотирьох конкретних нових чемпіонів: частина могла прийти, а частина — вийти.

|---|---:|---:|

| Лояльні | 1 | 2,4% |
| Перспективні | 2 | 4,8% |
| Потребують уваги | 0 | 0% |
| Сплять | 1 | 2,4% |
| Втрачені | 1 | 2,4% |

### 26.2. Контрольний розподіл після

| Сегмент | Кількість | Частка |
|---|---:|---:|
| Чемпіони | 37 | 88,1% |
| Лояльні | 1 | 2,4% |

Нульові сегменти у легенді можуть бути приховані.

## 27. Матриця переходів

Рядки — RFM-сегмент до.

Колонки — RFM-сегмент після.

### 27.1. Правила читання

- сума рядка дорівнює значенню відповідного сегмента у donut `ДО`;
- сума колонки дорівнює значенню donut `ПІСЛЯ`;
- діагональ — без змін;
- зелене — перехід у кращий сегмент;
- червоне — перехід у гірший;
- порожня клітинка показується крапкою.

### 27.2. Контрольна матриця 42

Ненульові переходи:

| До | Після | Кількість | Напрямок |
|---|---|---:|---|
| Чемпіони | Чемпіони | 35 | без змін |
| Чемпіони | Лояльні | 1 | вниз |
| Чемпіони | Перспективні | 1 | вниз |
| Лояльні | Чемпіони | 1 | вгору |
| Перспективні | Втрачені | 2 | вниз |
| Сплять | Чемпіони | 1 | вгору |
| Втрачені | Перспективні | 1 | вгору |

Перевірка руху:

- вгору: `1 + 1 + 1 = 3`;
- без змін: `35`;
- вниз: `1 + 1 + 2 = 4`.

### 27.3. Перевірка marginals

Наприклад:

- рядок `Чемпіони`: `35 + 1 + 1 = 37` до;
- колонка `Чемпіони`: `35 + 1 + 1 = 37` після;
- колонка `Втрачені`: `2` після.

## 28. Найважливіше методологічне обмеження

Сторінка не вимірює причинний ефект кампанії.

Вона має лише:

- treated audience;
- період до;
- період після.

Вона не має:

- контрольної групи;
- holdout-аудиторії;
- matched control;
- difference-in-differences;
- статистичної значущості;
- довірчих інтервалів;
- поправки на сезонність;
- поправки на інфляцію;
- даних про інші кампанії;
- вартості кампанії;
- маржі;
- ROI/ROAS;
- attribution model.

Тому правильна назва метрики:

`оборот сегмента після кампанії`.

Некоректно без додаткового аналізу називати її:

- додатковим оборотом;
- інкрементальною виручкою;
- доходом, створеним кампанією;
- причинним uplift-ом.

### 28.1. Що потрібно нашій програмі

Мінімальний покращений дизайн:

```text
treated_before
treated_after
control_before
control_after

incremental_lift =
    (treated_after - treated_before)
    - (control_after - control_before)
```

Також потрібні:

- абсолютний uplift;
- відносний uplift;
- incremental buyers;
- incremental revenue;
- cost per reactivated customer;
- campaign cost;
- incremental margin;
- confidence interval;
- significance або Bayesian probability of uplift.

### 31.1. Немає existence validation

Найсерйозніший методологічний ризик.

### 31.5. Top-200 без повного списку

Немає пагінації та експорту.

### 31.6. Неясна recency

Не відомий знаменник і правило для неактивних.

### 31.7. Не показані RFM-пороги

Не можна незалежно відтворити класифікацію лише з цієї сторінки.

### 31.8. Немає campaign metadata

Відсутні:

- назва кампанії;
- канал;
- оффер;
- час відправлення;
- вартість;
- контрольна аудиторія;
- ціль;
- owner.

### 31.9. Немає churn rate на верхній картці

Є кількість відпалих, але немає `dropped / active_before`.

### 31.10. Неактивні обох періодів приховані у верхній зоні

`Не повернулись` видно лише нижче.

### 36.3. Періоди

- 1 день;
- 7 днів;
- 30 днів;
- високосний лютий;
- перехід року;
- timezone;
- DST;
- майбутні дати;
- відсутність даних.

### 36.4. Поведінковий баланс

`reactivated + retained + dropped + not_returned = matched_segment_size`.

`reactivated + retained = buyers_after`.

`retained + dropped = active_before`.

### 36.5. Грошовий баланс

Сума daily after дорівнює money after.

Сума customer after turnover дорівнює агрегованому turnover, якщо таблиця береться без Top-200 обрізання.

### 36.6. RFM matrix

- суми рядків = before donut;
- суми колонок = after donut;
- diagonal = stable;
- green cells = up;
- red cells = down;
- total matrix = matched segment size.

### 36.7. Нульові знаменники

- money before = 0;
- checks before = 0;
- inactive before = 0;
- active before = 0;
- segment size = 0.

Не можна безумовно показувати 0,0% там, де математично результат undefined.

### 36.8. Draft vs analyzed

Змінити файл після аналізу й переконатися, що UI чітко маркує старий звіт.

### 36.9. Конкурентність запитів

Швидко змінити дати кілька разів. Стара відповідь не повинна перезаписати нову.

### 36.10. Privacy

Перевірити tenant isolation, audit, file retention, logs та експорт.

## 37. Межі підтвердженого знання

Сторінка не розкрила:

- точний список назв колонок для auto-detection;
- поведінку при неоднозначних числових колонках;
- фактичне застосування ліміту 50 000;
- правила encoding і separator detection;
- максимальний розмір файлу;
- timezone;
- обробку повернень і скасувань;
- чи turnover є gross або net;
- точну recency formula;
- R/F/M thresholds;
- RFM model version;
- правила для анонімних чеків;
- правила identity merge;
- точні recommendation thresholds;
- спосіб обробки division by zero;
- повний склад Top-200 при однаковому обороті;
- можливість експорту через прихований API;
- статистичну причинність результату.

Ці пункти не можна копіювати як підтверджену поведінку. Їх потрібно визначити продуктовими рішеннями.

## 38. Підсумкова специфікація

Сторінка є зручним post-campaign dashboard для завантаженої аудиторії.

Її основна логіка:

```text
імпорт ID
-> рівні before/after вікна
-> поведінковий статус
-> агреговані R/F/M
-> індивідуальні RFM-переходи
-> рекомендації
```

Для власної програми варто зберегти:

- простий імпорт;
- рівні часові вікна;
- чотири взаємовиключні поведінкові стани;
- daily turnover;
- R/F/M cards;
- таблицю transition per ID;
- before/after donuts;
- migration matrix;
- рекомендації.

Критично потрібно виправити:

- перевірку існування ID;
- строгий parser;
- позначення незастосованої чернетки;
- повний список замість Top-200;
- прозору recency;
- формули й знаменники;
- причинні твердження без control group.

Найкраща версія нашого аналога повинна розділяти два рівні висновків:

1. **Факт:** як змінилась поведінка сегмента до та після.
2. **Оцінка ефекту:** яка частина зміни інкрементально спричинена кампанією.

Саме другого рівня конкурентна сторінка наразі не має.
